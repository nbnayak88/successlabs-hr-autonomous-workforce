# Product Prototyping Lab — General Handbook

**Lab:** Product Prototyping Lab (PDL)  
**Track:** 13 — Product Management  
**Learning Intent:** **PROTOTYPE**  
**Maturity Stage:** Advanced  
**Core Intention:** Convert reusable knowledge into scalable consulting accelerators and frameworks.  
**Student Outcome:** Develop a productization mindset.

> **Knowledge used once is a service; knowledge made reusable is leverage.** PDL develops the ability to recognize repeatable patterns, turn expertise into prototypes and reusable assets, validate adoption and scale impact.

---

# 1. Purpose

PDL converts **experience and expertise into reusable products, accelerators, frameworks, templates and tools**.

The productization loop is:

**Observe → Identify Pattern → Frame Problem → Prototype → Test → Refine → Productize → Adopt → Measure → Scale**

The objective is not to create more artifacts. It is to create **assets that repeatedly solve meaningful problems**.

---

# 2. PDL Philosophy

1. **Prototype is your intent** — turn reusable knowledge into scalable assets.
2. **Build once, reuse repeatedly** — design for repeatable value.
3. **Templatize your thinking** — make expertise transferable.
4. **Design for adoption** — usefulness is proven through use.
5. **Capture patterns, not one-offs** — productize recurring problems.
6. **Operate at the Advanced level** — think like a product owner, not only a practitioner.
7. **Scale across the 11 GICS sectors** — design for flexibility and breadth.
8. **Productization serves the mission** — reusable assets can extend better experiences farther and faster.

# 6. Pattern Discovery

Look for repeated:

- Questions
- Deliverables
- Analysis activities
- Workshops
- Calculations
- Decision processes
- Assessments
- Templates
- Configurations
- Troubleshooting approaches
- Reporting needs
- Training activities
- Consulting recommendations

A repeated activity is not automatically a product opportunity.

Validate:

**Frequency + Pain + Repeatability + Reusability + Adoption Potential**

---

# 7. Problem-to-Prototype Framework

Use:

**Problem → User → Job-to-be-Done → Desired Outcome → Hypothesis → Prototype → Feedback → Revision**

Define the hypothesis explicitly:

> “We believe **[user]** can achieve **[outcome]** by using **[prototype]**, because **[reason/evidence]**.”

Then test it.

---

# 8. Minimum Viable Prototype

The first prototype should answer the most important uncertainty.

Prototype only enough to test:

- User need
- Concept
- Workflow
- Experience
- Feasibility
- Value hypothesis

Possible prototype forms:

- Canvas
- Checklist
- Template
- Calculator
- Assessment
- Dashboard
- Workflow
- Prompt
- AI assistant
- Agent
- Knowledge product
- Micro-application
- Consulting accelerator

> **Prototype the uncertainty, not the entire product.**

# 9. Reusable Asset Architecture

Every reusable asset should define:

### Purpose
What problem does it solve?

### Inputs
What does the user provide?

### Steps
What does the user do?

### Outputs
What does the asset produce?

### Roles
Who uses or owns it?

### Rules
What constraints apply?

### Examples
How should it be used?

### Version
Which version is current?

### Feedback
How is improvement captured?

### Usage
Where has it been successfully applied?

---

# 10. Design for Adoption

A reusable product should be:

- Clear
- Discoverable
- Self-explanatory
- Easy to start
- Easy to apply
- Consistent
- Adaptable
- Measurable

Use:

**Discover → Understand → Try → Use → Repeat → Recommend**

If users repeatedly need the creator to explain the asset, productization is incomplete.

---

# 11. Product Quality Model

Evaluate the prototype across:

### Problem Fit
Does it address a meaningful recurring problem?

### User Fit
Does the intended user understand and need it?

### Usability
Can users apply it without unnecessary friction?

### Reusability
Can it work repeatedly?

### Adaptability
Can it flex across contexts?

### Reliability
Does it produce consistent results?

### Evidence
Is usefulness demonstrated?

### Scalability
Can adoption grow without equivalent growth in creator effort?

### Maintainability
Can it evolve without becoming fragile?

# 12. Feedback & Iteration Loop

Use:

**Observe → Capture → Prioritize → Change → Test → Measure**

Collect:

- User feedback
- Usage data
- Completion rates
- Time saved
- Error patterns
- Adoption barriers
- Requests
- Failure modes
- Outcome evidence

Do not treat every feature request as a requirement.

Prioritize based on:

**User Value + Strategic Value + Evidence + Effort + Risk**

# 13. Product Roadmap

A product roadmap should distinguish:

### Now
What must solve the core problem?

### Next
What improves adoption or value?

### Later
What enables scale or differentiation?

### Explore
What emerging opportunity deserves investigation?

For each roadmap item:

**Problem → Outcome → Hypothesis → Priority → Evidence → Release**

---

# 14. Product Troubleshooting

### Asset is not being used
Review discoverability, clarity, usability and problem relevance.

### Users request extensive customization
Determine whether the underlying pattern is poorly defined or the product needs configurable boundaries.

### Prototype works for one client only
Separate reusable core from client-specific implementation.

### Users need constant explanation
Improve embedded guidance, examples and interface design.

### Many features but little value
Return to the core user problem and outcome.

### High interest but low adoption
Investigate workflow friction, ownership, incentives and usability.

### Asset becomes difficult to maintain
Reduce unnecessary complexity and establish product ownership.

### Prototype succeeds but cannot scale
Review architecture, operating model, automation and support requirements.

---

# 15. Product Metrics

Measure outcomes rather than features shipped.

Useful indicators include:

- Active users
- Adoption rate
- Repeat usage
- Completion rate
- Time saved
- Error reduction
- Cycle-time improvement
- Outcome improvement
- User satisfaction
- Reuse across engagements
- Support effort
- Conversion from prototype to production
- Cost to maintain
- Value created per unit of creator effort

> **A shipped feature is an activity. A changed outcome is evidence of value.**

# 19. PDL Rule Book — Operationalized

### Do
- Build reusable assets.
- Productize recurring problems.
- Turn expertise into templates and accelerators.
- Design for adoption.
- Capture patterns across engagements.
- Think like a product owner.
- Make assets self-explanatory.
- Iterate from real usage.
- Measure product impact.
- Design for cross-sector reuse.

### Don't
- Solve the same problem from scratch repeatedly.
- Keep reusable knowledge locked in your head.
- Build assets nobody can use.
- Productize one-off solutions without a repeatable pattern.
- Optimize for creator convenience alone.
- Assume version one is final.
- Ship features without evidence of value.
- Make every client customization part of the core product.
- Ignore maintenance.
- Confuse an artifact with a product.
